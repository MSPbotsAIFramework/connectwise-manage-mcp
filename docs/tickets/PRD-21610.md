## Requirement understanding

One line: Add a `cw_list_agreement_types` tool to the ConnectWise Manage MCP so agreement/contract types can be listed, needed by EMD Networking Services' Rewst flow that syncs CW Manage agreement tiers to NinjaOne org fields.

Restatement: This ticket is item 44 of the Rewst → MSPbots migration gap register. EMD Networking Services runs a Rewst flow ("HB - Sync CW Manage Services Tier to Ninja Org Fields", 35 runs in the last 365 days, evidence grade A) that calls ConnectWise's `cw_manage.list_agreement_types` action to read the list of agreement types (`id`, `name`, `inactiveFlag`, `defaultFlag`, `billingCycle`) and writes the matching tier onto a NinjaOne organization custom field. The MSPbots ConnectWise Manage connector is already connected but, per the gap register's 92-tool audit, has no tool that reads `GET .../finance/agreements/types` — it has agreement (contract) tools (`cw_search_agreements`, `cw_get_agreement`, ...) but nothing for the agreement *type* reference table. Success is a new read-only tool that lists agreement types with the same filter/paging shape as the rest of the connector, so this Rewst flow (and any other agent) can be rebuilt against MSPbots without losing this lookup.

## Product design

### Goals / Non-goals

**Goals**
- Add one read-only MCP tool, `cw_list_agreement_types`, that lists ConnectWise Manage agreement (contract) types, so Rewst-equivalent flows reading `GET /finance/agreements/types` can be rebuilt on the MSPbots connector.
- Keep the same filter/paging contract (`conditions`, `fields`, `orderBy`, `page`, `pageSize`) as the other reference-table list tools in this connector, so downstream agents can treat it consistently.

**Non-goals**
- No create/update/delete on agreement types — the gap register only asks for a read (`cw_manage.list_agreement_types` is a list action); ConnectWise agreement types are typically configured once in the PSA admin UI, not managed by automations.
- No `childConditions` / `customFieldConditions` parameters — not requested, and no existing simple reference-table tool in this connector exposes them (see Current state).
- Does not touch the existing agreement (contract) tools (`cw_search_agreements`, `cw_get_agreement`, ...) — those model agreement *instances*, this models the type reference table they point to.

### Acceptance criteria

- **AC1** — Given valid `X-CW-*` credential headers, when an agent calls `cw_list_agreement_types` with no arguments, then the response is `{"items": [...], "count": n, "page": 1, "page_size": 25, "has_more": bool}` listing ConnectWise agreement types (same envelope as every other list tool in this connector).
- **AC2** — Given a `conditions` argument (e.g. `inactiveFlag = false`), when calling `cw_list_agreement_types`, then only agreement types matching that ConnectWise conditions string are returned.
- **AC3** — Given a `fields` argument (e.g. `"id, name"`), when calling `cw_list_agreement_types`, then each returned item is restricted to the requested fields.
- **AC4** — Given an `orderBy` argument, when calling `cw_list_agreement_types`, then ConnectWise's ordering for that field is reflected in the returned list (pass-through, not re-sorted client-side).
- **AC5** — Given more agreement types than fit on one page, when calling `cw_list_agreement_types` with `page`/`pageSize`, then paging behaves like every other list tool: default `pageSize` 25, cap 200, `has_more` true when a further page exists.
- **AC6** — Given a request missing or blank `X-CW-*` credential headers, when calling any tool including `cw_list_agreement_types`, then the server returns 401 with the list of expected headers (existing cross-cutting behavior — regression check, no tool-specific code).
- **AC7** — Given the connector's `tools/list`, then `cw_list_agreement_types` is present with name, description and input schema consistent with the other `add_search`-based list tools, and no existing tool's name or schema changed (contract-compatibility check against `tools_baseline.json`).
- **AC8** — Given the README's Tools table, then the Agreements row lists `cw_list_agreement_types` and the total tool count reads 93 (was 92).

### Open questions

- None blocking. One non-blocking assumption: the response passes through whatever fields ConnectWise's `/finance/agreements/types` API returns (after the existing `*_href` stripping), rather than hard-restricting to the gap register's `id`/`name`/`inactiveFlag`/`defaultFlag`/`billingCycle` subset — this matches how every other `add_search` tool in the repo works (no field allow-list) and lets `fields`/`conditions` reach any field ConnectWise exposes on that endpoint. If the real endpoint returns additional fields, no design change is needed; the doc proceeds on this assumption.

## Tech design

### Conclusion

Add `cw_list_agreement_types` to `src/connectwise_manage_mcp/tools/finance.py` using the existing `add_search()` factory against `GET /finance/agreements/types`, in the Agreements area, immediately after `cw_get_agreement`. This is a same-shape addition to an existing, actively maintained repo (not a new MCP, not a gateway change) — no option analysis beyond "reuse `add_search`" is warranted; the repo's own `cw_list_boards` / `cw_list_priorities` / `cw_list_work_types` / `cw_list_work_roles` tools are the direct precedent for a simple vendor reference-table lookup.

### Option analysis

Only one real option: reuse `add_search()` against `/finance/agreements/types`, matching `cw_list_boards`/`cw_list_priorities`/`cw_list_work_types`/`cw_list_work_roles`. Considered and rejected:

- **Hand-written tool function (like `cw_get_agreement_additions`)** — rejected. `add_search` already provides exactly the parameter set the gap register's own "input parameters" list asks for (`conditions`, `fields`, `orderBy`, paging); a hand-written function would just reimplement it with more code and a higher chance of drifting from the rest of the connector's list-tool behavior (truncation, `*_href` stripping, error envelope).
- **Expose `childConditions`/`customFieldConditions`** — rejected (see Non-goals): not requested, no precedent among the repo's simple reference-table tools, and `/finance/agreements/types` is a small, flat lookup table where a child-collection filter has no obvious use (unlike `cw_search_contacts`, which filters the contact-types child collection for a genuine reason).

### Data & API contract

- **Upstream endpoint**: `GET {CW Manage API}/v4_6_release/apis/3.0/finance/agreements/types` (per `api.py`, the client prefixes this automatically; tools pass the path only, e.g. `/finance/agreements/types`).
- **Tool**: `cw_list_agreement_types`
  - Params (all optional): `conditions: str` (ConnectWise conditions query string, e.g. `inactiveFlag = false`), `page: int`, `pageSize: int` (default 25, cap 200, per repo-wide convention), `orderBy: str`, `fields: str | list[str]` (repo's existing `Fields` type).
  - Response (JSON string): `{"items": [...], "count": n, "page": p, "page_size": s, "has_more": bool}` — identical envelope to every other `add_search` tool.
  - Item shape: whatever ConnectWise returns for this endpoint, with `*_href` links stripped (existing `clean()`/`list_result()` behavior). The gap register's "fields used downstream" are `id`, `name`, `inactiveFlag`, `defaultFlag`, `billingCycle` — all ordinary top-level fields, nothing requiring special mapping (no literal/date-bracket conditions quirks like contacts' `name` rewrite).
  - Errors: existing envelope, `{"error": {"code": ..., "message": ..., "retryable": bool}}`, codes `not_configured` / `unauthorized` / `not_found` / `invalid_argument` / `rate_limited` / `upstream_error` — no new error code needed.
- **Backward compatibility**: pure addition. No existing tool name, parameter, or response shape changes. `tests/test_tools.py`'s baseline diff enforces this mechanically.

### Key flow / sequence

1. Agent calls `cw_list_agreement_types` (optionally with `conditions`/`fields`/`orderBy`/`page`/`pageSize`) via the MCP gateway, which attaches the tenant's `X-CW-*` credential headers.
2. Middleware (`credentials.py`, unchanged) validates headers are present, sets the per-request `ContextVar`.
3. `add_search`'s generated handler builds `params` and calls `client.get_page("/finance/agreements/types", params)`.
4. `CWClient` (unchanged) issues the ConnectWise REST call, retries on 429/5xx/timeout per existing policy, maps errors to the standard envelope.
5. `list_result()` wraps the page into `{"items", "count", "page", "page_size", "has_more"}`, truncating if over 20,000 characters (unchanged shared logic).
6. Response JSON string returned to the agent.

No new sequence — this is the same flow as `cw_list_work_types`/`cw_list_priorities`, just against a different upstream path.

### Non-functional

- **Idempotency/concurrency**: read-only GET, no state; same statelessness guarantee as every other tool (`stateless_http=True`, no module-level mutable state) — unaffected.
- **Performance**: agreement types are a small, rarely-changing reference table (bounded by how many tiers a ConnectWise org configures, typically well under the 200-row page cap); no pagination-storm risk.
- **Security / multi-tenancy**: credentials come only from the request's `X-CW-*` headers (existing middleware), never cached or shared across requests — unchanged. No new data exposure: this is read access to a reference table already indirectly reachable (ConnectWise "security role" permissions on `finance/agreements/types` gate it server-side, same as every other tool).
- **Observability**: no new logging needs — errors flow through the existing structured envelope; no credentials or PII in agreement type names.
- **Rollout risk**: none — single additive tool registration behind the existing stateless HTTP server; no schema migration, no config flag.

### Rollout & rollback

- **Rollout**: merge to `main` (the only deploy target for this repo), then the review leg publishes `main` to INT via `mcppub publish` (existing mechanism, no new credential/registration step — `connectwise-manage-mcp` is already a registered vendor).
- **Rollback**: revert the single commit (or `git revert`); the tool simply disappears from `tools/list` on the next INT deploy. No data migration, no stored state to unwind.
- **Feature flag**: none needed — this is a pure additive, read-only MCP tool; no reason to gate it behind a flag given the non-functional analysis above.
