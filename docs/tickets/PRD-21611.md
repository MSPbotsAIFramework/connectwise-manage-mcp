## Requirement understanding

One line: Add a cw_update_configuration tool to the ConnectWise Manage MCP connector so an agent can update a configuration item (asset/CI) -- rename it, set it Inactive, and write back hardware fields such as RAM/OS/IP -- which today has no corresponding tool.

This ticket is item 45 of the Rewst-to-MSPbots migration gap register, sourced from a real Rewst flow at "EMD Networking Services" that calls ConnectWise Manage's `cw_manage.update_configuration` action (`PATCH {CW Manage API}/v4_6_release/apis/3.0/company/configurations/{id}`) to rename configuration items, deactivate them, or update hardware attributes. The requester verified on 2026-10-28 that none of the connector's 92 existing tools cover this — `cw_update_ticket_configurations` only attaches/detaches a configuration to a service ticket, it does not edit the configuration item itself. The ask is to add the missing update tool so this class of Rewst automation can be reproduced as an MCP tool call.

## Product design

### Goals / Non-goals

Goals:
- An agent calling the ConnectWise Manage MCP connector can update an existing configuration item's fields (name, status, active flag, company/type reference, hardware/network fields, custom fields) without needing a connector call outside the documented tool set.
- The new tool follows the same contract shape, error envelope, and compatibility guarantees as the connector's other update tools (`cw_update_company`, `cw_update_ticket`): JSON Patch operations, one tool call per configuration item, no side effects beyond the fields explicitly patched.
- Existing tools and their parameters are unaffected (additive only).

Non-goals:
- Not adding bulk/batch update across multiple configuration items in one call (none of the sibling update tools do this either).
- Not adding a delete-configuration tool — ConnectWise Manage configurations are deactivated via `activeFlag`/`status`, not deleted (same convention the connector already uses for contacts, `README.md:145`).
- Not changing `cw_update_ticket_configurations` or any other existing tool.
- Not touching anything outside this one MCP repo — no platform (Code Repo) change, no MCP gateway change.

### Acceptance criteria AC1..ACn

- AC1: Given a valid configuration item ID and a JSON Patch array that includes `replace /name`, when `cw_update_configuration` is called, then the tool issues `PATCH /company/configurations/{id}` with exactly those operations and returns the updated configuration object as a JSON string (same response shape as `cw_get_configuration`/`cw_update_company`).
- AC2: Given operations that set `status/id` and `activeFlag` together (the Rewst example: rename + mark Inactive), when the tool is called, then both changes are sent in one PATCH request and both appear in the returned object.
- AC3: Given an `operations` array containing an `add` or `replace` operation with no `value`, when the tool is called, then it returns the structured error envelope with `code: "invalid_argument"` and does not call the ConnectWise API (same validation behavior `cw_update_ticket` already has).
- AC4: Given an empty `operations` array, when the tool is called, then it returns `invalid_argument` without calling the API.
- AC5: Given the ConnectWise API returns an error (e.g. configuration not found, permission denied), when the tool is called, then the error is mapped through the existing `ApiError` → structured envelope path (`not_found` / `unauthorized` / etc.), consistent with every other tool in this connector.
- AC6: Given the tool is added, when `tools/list` is called, then all 92 existing tools are unchanged (name, required/optional parameters, types) and `cw_update_configuration` appears as tool #93, per `AGENTS.md`'s backward-compatibility rule.
- AC7: Given no real ConnectWise account/credentials are available at design or dev time, that does not block this ticket (vendor-mcp rule: a missing vendor test account is not a blocker) — AC1-AC6 must be covered by tests against a mocked ConnectWise API (respx), consistent with how `cw_update_company`/`cw_update_ticket` are already tested.

### Open questions

- Q1 (not blocking, assumption applied): the ticket lists specific field names (`name`, `status{id}`, `activeFlag`, `company{id}`, `type{id}`, `osInfo`, `osType`, `ram`, `cpuSpeed`, `ipAddress`, `macAddress`, `serialNumber`, `modelNumber`, `manufacturer{id}`, `lastLoginName`, `customFields[]`) as if they were individual tool parameters. The connector's existing convention for single-resource PATCH endpoints (`cw_update_company`, `cw_update_ticket`) is a generic `operations: Operations` (JSON Patch) parameter rather than one named parameter per field. This keeps the tool usable for any configuration field ConnectWise supports (not only the ones listed), matches `AGENTS.md`'s compatibility rule (a fixed field list would need a signature change every time a new field is needed — an unbounded, never-finished parameter list), and matches exactly how the Rewst example body in the ticket (`{"name": ..., "status": {"id": ...}, "activeFlag": false}`) maps to patch paths (`name`, `status/id`, `activeFlag`). Assumption applied: build `cw_update_configuration` as a generic JSON-Patch tool like its siblings, not a field-enumerated one. If product wants a field-enumerated signature instead, say so in a comment and move this ticket back to `5b - ready for groom`.

No open question is marked "blocks implementation": the generic-PATCH shape is the connector's established pattern, reduces rather than adds risk, and the assumption is reversible without discarding any other part of this design.

## Tech design

### Conclusion

Add one new tool, `cw_update_configuration`, to `src/connectwise_manage_mcp/tools/system.py`, implemented exactly like the existing `cw_update_company` (`tools/companies.py:129-144`): a JSON-Patch update against `PATCH /company/configurations/{id}`, reusing the connector's existing `Operations` / `patch_ops` / `CWClient.patch` / `clean` helpers. No new dependencies, no schema/DB change (this connector is stateless and has none), no change to any existing tool.

### Option analysis

- **Option A (chosen): generic JSON-Patch tool, same shape as `cw_update_company`/`cw_update_ticket`.** Reuses 100% of existing infrastructure (`Operations`, `patch_ops`, `CWClient.patch`), adds zero new code paths and zero new dependencies, and covers every field ConnectWise's configuration-item PATCH endpoint supports (not only the ones the ticket happened to list) because the caller supplies the patch paths. This is "reuse first": the connector already solved "update one resource by ID with JSON Patch" twice; a third hand-rolled variant (Option B) would be exactly the duplication the skill's code-quality rule flags.
- **Option B (rejected): one named parameter per field** (`name`, `status_id`, `active_flag`, `ram`, `ip_address`, ...). Matches the ticket's literal field list more closely at first glance, but: (1) breaks the moment ConnectWise adds, or the business needs, a field not on that list — a signature change, and `AGENTS.md`'s compatibility rule treats growing a tool's parameter list over time as a real, unbounded cost; (2) duplicates validation/serialization logic `patch_ops` already provides; (3) none of this connector's other single-resource updates use this shape — it would be inconsistent with `cw_update_company` and `cw_update_ticket` sitting right next to it in the same file area.
- **Option C (rejected): extend `cw_update_ticket_configurations`** to also allow editing a configuration's own fields. Rejected because that tool's contract (ticket-association add/remove, batched, continue-on-failure) is a different operation from "edit one configuration item," and `AGENTS.md` forbids changing an existing tool's parameters/behavior in ways that could surprise agents already calling it for association changes.

### Data & API contract

Tool: `cw_update_configuration`
- Input: `id: int` (Configuration item ID, required), `operations: Operations` (non-empty JSON Patch array, required) — identical shape to `cw_update_company`.
- Behavior: validates operations via `patch_ops()` (rejects `add`/`replace` without `value`, rejects malformed paths); calls `CWClient.patch(f"/company/configurations/{seg(id)}", ops, idempotent=replace_only)`; returns `clean(response)` as a JSON string.
- Upstream request: `PATCH {ConnectWise base URL}/v4_6_release/apis/3.0/company/configurations/{id}` with body = the JSON Patch array (ConnectWise's native PATCH format, matching the ticket's own citation).
- Output: the updated configuration object (same shape `cw_get_configuration` returns), JSON-encoded string.
- Errors: structured envelope `{"error": {"code", "message", "retryable"}}` via the connector's existing `ApiError` mapping (`not_configured` / `unauthorized` / `not_found` / `invalid_argument` / `rate_limited` / `upstream_error`) — no new error codes.
- Backward compatibility: purely additive; no existing tool's request/response contract changes. `tests/test_tools.py` is the automated check for this.

### Key flow / sequence

1. Agent calls `cw_update_configuration(id=12345, operations=[{"op":"replace","path":"name","value":"SRV-EMD-01 - Inactive"},{"op":"replace","path":"status/id","value":7},{"op":"replace","path":"activeFlag","value":false}])` — the Rewst example from the ticket, translated to JSON Patch.
2. `patch_ops()` validates each operation (path format, `value` present for `add`/`replace`) and determines `replace_only` (all ops are `replace` → the request is safe to retry).
3. `CWClient.patch()` sends `PATCH /company/configurations/12345` with the operations array, honoring the connector's existing retry/backoff rules (idempotent PATCHes retried on 5xx/timeout, same as `cw_update_company`).
4. ConnectWise returns the updated configuration object; `clean()` strips `*_href` links; the tool returns the JSON string.
5. On any upstream error, the existing `ApiError` → envelope mapping runs unchanged.

### Non-functional

- **Idempotency/concurrency**: inherits the connector's existing per-request statelessness (no shared state, credentials from headers only, per `AGENTS.md`) and the existing retry policy (`idempotent=replace_only`, same as `cw_update_company`) — no new concurrency concerns since this tool introduces no state.
- **Performance**: single PATCH call, same cost profile as `cw_update_company`; the connector-wide 100-second-per-call ceiling (`README.md:151`) applies unchanged.
- **Security / multi-tenant isolation**: credentials come only from the per-request `X-CW-*` headers (`credentials.py`), never cached or shared across requests — this tool adds no new credential path and follows the same per-request isolation as every other tool in the connector. No data beyond what ConnectWise already returns for a configuration item (hostnames, serial numbers, IPs) is logged; the connector does not log tool arguments by default.
- **Observability**: tool calls are already logged by the MSPbots MCP gateway's audit trail (who / which vendor / when, `README.md:60`); no connector-level logging change needed.

### Rollout & rollback

- Additive change to a stateless service; no data migration, no feature flag needed (same rollout shape as every prior tool addition to this connector, e.g. PRD-20969).
- Rollback = revert the commit; no persisted state to undo.
- Release order: not applicable — only this one MCP repo is touched, no platform or second-repo dependency. `Track: vendor-mcp`, single repo.

### Test strategy

- Unit/handler tests (respx-mocked ConnectWise API), added to `tests/test_handlers.py`, mirroring `test_update_ticket_sends_json_patch` / `test_patch_add_without_value_is_rejected` (`tests/test_handlers.py:154-163`):
  - sends the right PATCH body for a multi-field patch (AC1, AC2)
  - rejects `add`/`replace` without `value` (AC3)
  - rejects an empty `operations` array (AC4)
  - maps a mocked 404 from ConnectWise to `not_found` (AC5)
- Compatibility test: `tests/test_tools.py`'s existing assertions, once `cw_update_configuration` is added to `ADDED` (AC6) — no manual test needed beyond adding the entry and regenerating the snapshot.
- No real ConnectWise account is available; all automated tests run against respx mocks (AC7), consistent with how every other tool in this connector is tested (there is no integration-test tier in this repo per `uv run pytest`).
- Full test case list with steps/expected results lives in the sibling `PRD-21611.ac.json`.
